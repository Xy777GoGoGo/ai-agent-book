03

为什么必须 attn_implementation="eager"?默认的 SDPA 或 FlashAttention 会怎样?

代码题零依赖

提示:想清楚"注意力权重矩阵"在推理优化里被省掉了什么,以及省掉它的代价与收益。

思考链路先想 30 秒
  1. 在 agent.py:196 找到这个参数,看它为什么写在 from_pretrained 里。
  2. 在 run_attention_experiment.py 的 capture() 里找一句异常信息,它会告诉你拿不到张量时会发生什么。
  3. 回忆 FlashAttention 的设计目标:它要减少的是什么?(不是减少计算量,而是减少 HBM 读写与中间矩阵落地。)
参考答案

eager 会真实物化权重矩阵。它把 [batch, heads, seq, seq] 的注意力权重算出来并留在内存里,所以 output_attentions=True 能拿到全部层的张量。

FlashAttention / SDPA 不会。它们是融合 kernel,把 softmax 与加权求和合并,刻意不把 seq×seq 的中间矩阵写回显存——这正是它们快的原因。于是 capture() 会直接 raise RuntimeError("model returned no eager-attention tensors")。这是故意 fail closed,而不是静默退回一个空结果。

代价:显存与计算随序列长度平方增长。580 个 token、多层多头、float32,单层就已经是百万级元素。这也解释了为什么这个实验只用 0.6B 小模型和短序列:不是不想用大模型,而是 eager 的平方成本不允许。

为什么 simple 是 9×9、generated 是 580×580?这两个矩阵测的是同一件事吗?

代码题零依赖

提示:注意"一次前向"和"逐步生成"的区别。矩阵形状里藏着实验设计。

思考链路先想 30 秒
  1. 读 run_attention_experiment.py 的 main(),找到两次 capture() 调用:第一次传 simple,第二次传什么?
  2. 看 simple 的 tokenize:提示词是 北京 的 天气 怎么样,且 add_special_tokens=False。数一下大概是几个 token。
  3. 再想:如果是"增量生成时的张量",每一步的形状应该是什么?和 580×580 对得上吗?
参考答案

simple 只把提示词(9 个 token)做一次前向,得到 9×9。

generated 先让模型生成一段包含 <think> 与最终答案的内容,再把拼好的整段 580 个 token 整体前向一次,得到 580×580。

它们是同一类东西——都是"整段一次前向"得到的完整 n×n 注意力矩阵,不是逐步生成时的增量张量(那样每一步只会多一行)。区别只在长度:9×9 能看清单个 query 的权重分配,而 580×580 才装得下思考区与答案区两个各自的自注意力三角形。

这也是为什么 region_indices() 要在 generated 的 token 序列里找 <think> 和 </think>——它需要把连续的行切成"思考区"和"答案区"再分别观察。
06

前端轨迹 JSON 里的 attention_matrix 和 npz 里的矩阵不是一回事。差别在哪?混淆会导致什么误判?

代码题易错

这是全实验最容易搞混的一处,也是很多"看到奇怪结论"的源头。

思考链路先想 30 秒
  1. 读 agent.py:246:attention_weights[0, :, -1, :].mean(dim=0)。注意下标 -1 取的是什么维度。
  2. 再读 visualization.py:70:它是怎么把一堆变长向量拼成一个矩阵的?填不满的位置填了什么?
  3. 对比 run_attention_experiment.capture():attentions[index][0].float().mean(dim=0),这里没有 -1。
参考答案

前端路径(agent.py):每一步只保存当时最后一行的向量,长度等于该步的序列长度,所以整体是阶梯形。可视化时用 np.zeros((steps, max_len)) 补齐成矩形,未填的位置全是 0。

证据路径(run_attention_experiment):保存完整 n×n 矩阵,每行每个 query 位置都有真实权重。

误判:补齐的 0 看起来像"注意力极低",但它其实是没有数据,不是"模型不关注"。比如在阶梯矩阵上算 sink 或位置偏好,会得到系统性偏低的结论;更糟的是有人会由此得出"注意力很稀疏"的结论,而那只是补零造成的视觉假象。

记住一句话:0 在这里有两种完全不同的含义——"被因果掩码挡住"(真实权重为 0)与"这里没有观测"(补零)。两者在数值上一样,在语义上相反。

07

因果三角是怎么被"数值验证"的?为什么不能靠看图判断?

代码题零依赖

提示:找 gate 名字里带 causal 的那一项,看它要求什么。

思考链路先想 30 秒
  1. 在 matrix_metrics() 里找 np.triu_indices(length, k=1)。注意 k=1 意味着不含对角线。
  2. 看它算出两个量:causal_upper_triangle_max 和 ..._sum。为什么两个都要?
  3. 再看 gate 的判定阈值,以及原理:causal mask 把未来位置的 logits 设成 -inf,softmax 后应该是多少?
参考答案

取严格上三角(第 j 列大于第 i 行,即"看未来"的位置)的全部元素,算最大值与总和。gate 要求 最大值 ≤ 1e-7。

我实测这 8 个矩阵的上三角最大值全部恰好是 0.0——因为 softmax 在 -inf 位置上的输出是精确的 0,不是"很小的数"。

为什么不能看图:热力图经过色图映射、对数缩放和插值,"看起来像三角形"既不可复现,也无法排除渲染误差;更关键的是,视觉判断无法区分"真的为 0"和"小到看不出来"。判据必须是可计算的、有明确阈值的、能贴进证据文件的。

同时保留 max 和 sum:max 抓"有没有单个位置违规",sum 抓"整体泄漏了多少"。极端情况下,一个很大的违规会被淡出视野,而 sum 能兜住。

08

attention sink 怎么定义、怎么算?第 0 层和第 27 层差多少?为什么会出现?

测量题有陷阱

提示:定义很简单,但"要不要把第 0 行算进去"会显著改变短矩阵的结果。

思考链路先想 30 秒
  1. 在 matrix_metrics() 里找 sink 的定义:matrix[:, 0].mean()。翻译成自然语言——它对哪一维取均值?
  2. 分层对比:层 0 / 13 / 27 的 sink 是递增还是递减?
  3. 想第 0 行这个特殊情况:第一个 token 作为 query 时,它能看见几个 key?它的 self-attention 必然是多少?
  4. 再回到 softmax 的硬约束:每行权重和必须为 1,模型能表达"谁都不关注"吗?
参考答案

定义:sink share = 第 0 列(第一个 key)在所有 query 行上的平均权重。它衡量"整张矩阵有多少注意力被倾倒到序列开头"。

实测(含第 0 行,与官方 matrix_metrics 口径一致):

矩阵层 0层 13层 27
simple(9×9)0.1470.7390.832
generated(580×580)0.0040.2800.732

明显的单调递增:浅层接近局部/对角,深层把大量权重堆到首 token。

成因:softmax 强制每行权重和为 1,模型无法表达"不关注任何东西"。当当前 token 与前面都不太相关时,这些"多余权重"必须落到某个稳定位置,序列开头的固定 token 就成了公共回收站。这是数学约束的产物,不是缺陷。

那个陷阱:第 0 行只有自己一个可见 key,所以 M[0][0] 恒为 1.000(8 个矩阵全部如此)。对 9×9 这种短矩阵,把这一行算进去会把 layer 0 的 sink 从 0.040 抬到 0.147(约 3.7 倍);对 580×580 则几乎无影响(0.731 与 0.732)。所以短矩阵报告 sink 时必须说明是否排除第 0 行,否则不同长度的结果不可比。

README 说最后一层 sink "通常 75–85%",但你实测 generated 是 73.2%。这算实验不合格吗?

判断题核心观念

这题考的是"观测值与验收门槛"的边界——很多实验翻车就翻在这里。

思考链路先想 30 秒

  2. 去 run_attention_experiment.py 里搜 observational_note,看作者自己怎么界定这个数值。
  3. 逐个检查 9 个 gate:有没有一条是关于 sink 大小的?
  4. 反过来想:如果把观测值当门槛,会发生什么行为?
参考答案

不算。README 说的是"通常",是经验区间;73.2% 与 75% 只差约 2 个百分点,在"头平均 + 单次运行 + 单一 prompt + 0.6B 小模型"的条件下完全合理。simple 那组在同一层是 83.2%,落在区间内,说明现象本身是稳定的。

position_mass_per_token 在测什么?为什么只取响应的后半段行?这个指标有什么局限?

测量题局限分析

提示:注意它切的是行还是列,以及分母是什么。

思考链路先想 30 秒
  1. 读 matrix_metrics() 第 61-77 行:thirds = np.array_split(arange(length), 3) 切的是哪个维度?
  2. response_rows = arange(max(0, length // 2), length) —— 为什么是后半段?
  3. 最后除以 max(1, len(response_rows) * len(indices)) —— 得到的是总量还是"每格平均质量"?
参考答案

它在测位置偏好:把 key 位置按三等分(开头/中间/结尾),只统计响应行(序列后半段)对每一段的平均注意力质量。这对应"Lost in the Middle"式的观察。

为什么只取后半段:序列前半段主要是 prompt 读入,那些 query 行还在"理解输入",不反映生成时的检索偏好。只保留后半段,才更接近"模型在回答时去哪找信息"。

实测 generated layer 27 的三段值为 0.0038 / 0.0005 / 0.0008(开头明显高);simple layer 27 为 0.269 / 0.038 / 0.026。

三个局限:

  1. length // 2 是粗糙切分,不区分 prompt 与生成边界——对 generated 矩阵,这个边界其实由 context_length 给定了,却没用上。
  2. 它除掉了"行数 × 列数",得到的是每格平均质量,绝对值很小;不同长度的矩阵之间只能比比值,不能比大小。
  3. 开头三分段同时包含 sink 和特殊 token(<|im_start|> 之类),所以"开头偏好"里混着 sink 的贡献,不是纯粹的语义位置偏好。

2-8 的状态栏注入在哪一步?为什么用 role: "user" 并且放在最后?

代码题零依赖

提示:位置和角色这两个选择,各自服务于一个不同的工程目标。

思考链路先想 30 秒
  1. 读 status_message():它返回的 role 是什么?
  2. 看两个 gate:status_at_end 和 same_base_trajectory,它们分别约束了什么?
  3. 回到正文 851 行,找"强制性的注意力引导"那句话;再想 KV Cache 对前缀稳定性的要求。
参考答案

它作为一条额外的 user 消息追加在轨迹末尾。status_message() 返回的正是 {"role": "user", "content": "<agent_status>..."}。三个 gate 共同锁定这件事:status_at_end 要求它确实是最后一条,same_base_trajectory 要求除它之外两条轨迹完全一致,control_has_no_status 要求对照组不含该标记。

放末尾:位置上最接近即将生成的新 token,能获得更高注意力权重——这正是"强制性的注意力引导"。

用 user 而不是 system:不动静态前缀。系统提示 + 工具定义是每轮都会被重读的静态前缀,如果改它,两条臂的前缀就不同了,既是混淆变量,也会破坏前缀缓存。

顺带一个可核对的事实:without_status_bar 是 873 个 token,with_status_bar 是 927 个,差 54。这个差值应该来自状态栏块本身,但仓库里没有保留 token 文本(证据 JSON 被 gitignore 了),所以无法逐字核对——这正好引向第 15 题。

两组的注意力统计几乎一样(sink 0.781 vs 0.782,对角 0.113 vs 0.112),但行为不同(对照组拒答 2/3,实验组 3/3)。这是否说明注意力可视化没用?

批判性统计口径

这是整套练习里最重要的一题。提示:先问"这个统计量能表达我想看的东西吗"。

思考链路先想 30 秒
  1. 状态栏要改变的是"注意力分布的空间结构"还是"全局平均值"?一个全矩阵均值能不能表达前者?
  2. 两个矩阵长度一样吗?873 与 927 的均值可以直接比吗?
  3. 每臂多少次生成?2/3 与 3/3 的差别在统计上意味着什么?
  4. 正文自己是怎么描述这个实验的定位的?
参考答案

不能这样推。三条理由,每条都独立成立:

  1. 统计口径不匹配。状态栏的作用是让注意力集中到那 54 个 token 上,而不是改变整张矩阵的均值。用全矩阵均值去比,天然把空间结构抹平了——就像用平均温度比较两个城市的气候差异。
  2. 矩阵长度不对等。873 与 927 的均值不是同一个基准上的量;而且长度本身就是一个混淆变量(见第 15 题)。
  3. 样本量太小。每臂 3 次生成,2/3 与 3/3 的差异在统计上几乎没有说服力。

正文自己也把它定位为"小规模的定性演示,给的是直觉",而量化结论来自另一套专门的基准。

正确的读法:要检验这个假设,应该做区域级统计——状态栏那一段 token 获得了多少注意力质量、思考 token 里"数数"行为的比例有没有下降。也就是说,不是可视化没用,而是选错了统计量。这题的核心结论是:合适的统计口径比可视化本身更重要。

classify() 用关键词判断"拒答"和"违规"。这套判据有什么风险?你会怎么改?

代码题假阳性/假阴性

提示:分别构造一个"该判拒答却没判"和"不该判拒答却判了"的例子。

思考链路先想 30 秒
  1. 读 classify()(约 213-233 行),把拒答线索词表逐个看一遍:"cannot call"、"can't call"、"won't call"、"not call"、"maximum"、"limit"、"3/3"、"three times"。
  2. 再读违规判据:"<tool_call>" in lowered and '"name": "phone_call"' in lowered。
  3. 对每个判据问:模型做一件正确的事时,会不会命中它?
  4. 再问:模型做一件错误的事时,会不会漏掉它?
参考答案

假阳性(把正确判成拒答):模型只要复述状态栏——"已达上限 3/3""reached the maximum"——就会命中 maximum、limit、3/3、three times。即使它随后照样发起了第 4 次呼叫,只要 <tool_call> 的格式没完全匹配上,就会被归成 REFUSAL。这些词太宽泛,它们描述的是"话题",不是"行为"。

假阴性(把违规判成无行为):违规判据要求字符串里同时出现 <tool_call> 和 "name": "phone_call"。如果模型用别的 JSON 写法(空格、单引号、函数名大小写不同)、把调用放进代码块、或走原生 tool_calls 字段而不是文本标记,就会被判成 OTHER,而不是 VIOLATION。

改法:

  • 优先用结构化证据:解析 API 返回的 tool_calls 字段、或直接查工具执行记录——"有没有真的拨号"是环境事实,不是文本判断。
  • 自由文本分类只作辅助,并且要区分"提到上限"与"因此拒绝执行"。
  • 把 OTHER 当作需要人工复核的类别,而不是静默归入"无行为"。一个分类器的 OTHER 比例本身就是它的健康指标。
这个坑和第一章讲的"护栏误拒绝"是同一类问题:只测"该拦的拦住了没有",不测"该放的放行了没有",最终会得到一个看起来很好、实际不可用的判据。

提示:从四个方向想——样本量、变量隔离、指标预注册、可复现性。

正文说"状态栏要用代码维护,别拿大模型去维护"。为什么?如果必须用 LLM 呢?

读书题机制

提示:比较"用 LLM 统计长历史"和"用原上下文直接推理"这两件事的计算结构。

思考链路先想 30 秒
  1. 让 LLM 一次性读完整段历史再吐统计,和不用状态栏、直接让它从历史里数——这两件事的难点一样吗?
  2. 代码做统计和模型做统计,哪个更容易出错?哪个更容易验证?
  3. 状态栏一旦写错,下游会核对吗?去正文找"模型几乎无条件地相信状态栏"那句。
参考答案

为什么别用 LLM:让它一次性读完整段历史再吐统计结果,等于把"扫描整段上下文"这个原始难题原封不动搬了个家——问题一点没解决,还多了一次出错机会。正文的实测是:20 行正则就能达到标准答案级准确度,而让前沿大模型一次性批量统计,在多数格子上反而出错,把下游准确率拖到比"根本不用状态栏"还低。

为什么错误代价高:模型几乎无条件相信状态栏——你写"3 次"它就当 3 次,不会去核对,也不会自己重算。所以状态栏写错,错误会原样传进最终答案。它既是有效的来源,也是投毒的入口。

如果必须用 LLM:逐条抽取、再由代码汇总,绝不让它一次性批量统计。并且把状态栏准确率当成一线生产指标持续监控,而不是上线前测一次。

这条经验可以推广成一句判据:能确定性计算的,不要交给概率模型。模型擅长"理解和取舍",不擅长"精确计数与汇总"。

这个实验和 KV Cache 是什么关系?为什么书把 2-2 放在 KV Cache 那一节里?

读书题零依赖

提示:热力图能直接看到两件事,它们分别对应 KV Cache 的动机和它的边界。

思考链路先想 30 秒
  1. 回到正文 481 行:每生成一个新 token,它的 Query 要和什么做匹配?要对什么加权求和?
  2. 如果每次都重算,代价随长度怎么变?缓存的是哪两个东西?
  3. 因果三角说明"未来 token 不参与当前计算",这对"前缀可复用"意味着什么?
  4. 正文 441 行举了一个"在开头加一行时间戳"的例子,它破坏了什么?
参考答案

热力图把 KV Cache 的动机摆出来了:每生成一个新 token,它的 Query 都要与前面所有 token 的 Key 做匹配,再对所有 Value 加权求和。若每次重算,代价随上下文长度增长;所以要把已经算过的 K 与 V 缓存起来复用。

因果三角还说明了边界:未来 token 不参与当前计算,所以一段前缀只要不变,它的 K/V 就可以一直复用。反过来,任何破坏前缀的改动都会让该位置之后的缓存失效——正文 441 行的例子(在开头插入一行时间戳)正是如此:一个看似无害的改动,让整条推理链路慢一个量级。

由此也能解释 2-8 的设计:状态栏放在末尾,既不修改静态前缀、不破坏缓存,又能获得靠近生成位置的高注意力权重。位置的选择同时服务于注意力和缓存两个目标。

附录 B · 纯标准库读取 npz(已在本机跑通)

把下面这段存成 read_npz.py 放在实验目录下即可运行。它不依赖 numpy / torch。

import ast, struct, sys, zipfile

def load_npy(zf, name):
    with zf.open(name) as f:
        assert f.read(6) == b"\x93NUMPY"
        major = f.read(1)[0]
        f.read(1)
        if major == 1:
            hlen = struct.unpack("<H", f.read(2))[0]
        else:
            hlen = struct.unpack("<I", f.read(4))[0]
        header = ast.literal_eval(f.read(hlen).decode("latin1").strip())
        data = f.read()
    rows, cols = header["shape"]
    code = "f" if header["descr"].endswith("4") else "d"
    n = rows * cols
    flat = struct.unpack("<%d%s" % (n, code), data[: struct.calcsize("<%d%s" % (n, code))])
    return [flat[i * cols : (i + 1) * cols] for i in range(rows)]

def describe(path):
    with zipfile.ZipFile(path) as zf:
        for name in sorted(zf.namelist()):
            m = load_npy(zf, name)
            n = len(m)
            sink = sum(r[0] for r in m) / n
            diag = sum(m[i][i] for i in range(n)) / n
            upper = max((m[i][j] for i in range(n) for j in range(i + 1, n)), default=0.0)
            print(f"{name:24} n={n:4} sink={sink:.3f} diag={diag:.3f} upper_max={upper:.1e}")

if __name__ == "__main__":
    describe(sys.argv[1])
